# Data Contracts

## Raw syslog observation

The durable raw store retains the original message and collector metadata needed for replay, troubleshooting, and later parser improvement.

Representative fields:

```text
timestamp
ingest_timestamp
device_timestamp
source_ip
source_port
hostname
host
facility
severity
appname
message
raw_message
parse_status
source_type
version
event_json
```

Rules:

- `timestamp` is the authoritative collector-side event time.
- `device_timestamp` is preserved separately when available.
- `raw_message` must survive normalization unchanged enough to support replay.
- parse failure is represented as metadata; it is not a reason to discard the event.

Current schema version: `1`.

Representative normalized fields:

```text
schema_version

device_timestamp
hostname

source_port

severity
appname

event_family
protocol

entity_key
state
repeat_count
attention_eligible
suppression_rule_id

```

Defaults are intentionally capture-first:

- unknown vendor/platform values remain `unknown`
- unknown event families remain valid observations
- `signal_type` defaults to `observation`
- `repeat_count` defaults to `1`
- `attention_eligible` defaults to `true`

The public collector-side normalizer implements this contract and has passed selected replay/parity, complete live shadow verification, and the forward-only production GX10 handoff gate. Raw collector backlog records remain the captured Vector JSON event representation described below and are preserved for replay/rollback.

The implemented integration package in `docs/NORMALIZER_PRODUCTION_INTEGRATION.md` first writes schema-version-1 events to a separate shadow spool. Each eligible raw backlog line maps to exactly one normalized line; file-level source/output hashes, canonical inventory hash, versions, counts, and summary classifications are retained in a durable ledger. Shadow mode is live and validated, but shadow output does not replace the current backlog until a separately authorized promotion gate passes.

The active promotion contract is forward-only. A protected plan identifies one inclusive first normalized source path. Verified shadow outputs at or after that path are copied into a separate handoff root using the original raw relative filename; pre-floor history is excluded. GX10 therefore continues to see the same strict `/spool/YYYY/MM/DD/HH/syslog-YYYYMMDD-HHMM.jsonl.zst` pattern and the same `source_files.remote_path` namespace. The completed live cutover, exact parity evidence, and retained rollback are in `docs/NORMALIZER_HANDOFF.md`.

## Parser contract

Vendor/event parsers return enrichment only. They may set fields such as vendor, OS family, protocol, signal type, entity identity, state, and structured attributes.

They may not control whether an event is captured or silently erase the raw observation.

Parser dispatch is ordered, first-match-wins, but parser exceptions fail open: the original normalized observation survives and parser-error metadata is recorded.

## Collector-to-GX10 backlog contract - current

The collector writes newline-delimited JSON with RFC 3339 timestamps into UTC hour-partitioned Zstandard files:

```text
/var/spool/vector-ai/YYYY/MM/DD/HH/syslog-YYYYMMDD-HHMM.jsonl.zst
```

The restricted SFTP chroot exposes the corresponding public path as:

```text
/spool/YYYY/MM/DD/HH/syslog-YYYYMMDD-HHMM.jsonl.zst
```

Each line is one JSON object from the captured Vector UDP/TCP normalization path. GX10 requires at least:

- `timestamp`: timezone-aware string
- `message`: string

GX10 retains the complete original JSON line in `event_json` and maps available collector fields into local columns. Missing optional metadata remains nullable/empty according to the captured SQLite contract.

Transport/file rules:

- only the exact filename pattern is eligible
- files remain authoritative on the collector and are fetched read-only
- GX10 waits for the captured settle interval
- Zstandard integrity is tested before atomic local publication
- size and SHA-256 are recorded in `source_files`
- `(source_file, record_number)` is the local replay/idempotency key

The recovered base contains exactly:

- `suppression_rules`

The exact recovered-base DDL is `components/gx10/sql/initialize.sql`. Item 25 deliberately extends that base with:

- `incident_transitions`
- 5 explicit incident indexes
- 5 incident foreign keys
- 4 append-only enforcement triggers

The extension DDL is `components/gx10/sql/incident-v1.sql`. The database is replaceable working state rather than the authoritative raw archive.

The separate unscheduled projector can add version-4 rows only from exact normalized schema-version-1 fields plus the existing local suppression rules; it performs no vendor/message reparsing. The installed incident engine consumes only those version-4 rows. The working incident tables and both projection/incident cursors remain empty until the managed-invocation gate passes.

## AI result contract

AI result records are intentionally thin. Representative fields:

```text
timestamp
incident_id
run_id
model
type
status
severity
first_seen
last_seen
occurrence_count
title
body
tags
raw_json
```

The collector validates result files before ingestion. Required text/timestamp fields and size/record-count limits are enforced at the validation boundary.

Current boundary status:

- collector write-only transport exists
- files must use JSONL and settle before inspection
- maximum file size is 256 KiB
- maximum record count is 100
- `timestamp`, `title`, and `body` are required and validated
- accepted files move to the ready area; invalid files move to quarantine with a reason
- Vector ingests ready records into the ClickHouse `ai_updates` table
- no GX10 producer for this contract was discovered

Therefore the schema is an active collector-side capability contract, not evidence that the current GX10 produces AI results.

## Incident contract - deterministic implementation

An incident is a durable deterministic object assembled from observations.

Target lifecycle:

```text
CANDIDATE -> OPEN -> RECOVERING -> RESOLVED
```

Incident state retains append-only evidence/transitions, first/last seen times, occurrence and canonical repeat counters, entity identity, current state, and exact 60-minute/180-minute/24-hour rolling context summaries.

The local LLM consumes an incident packet and returns analysis; it does not become the canonical incident database.

The deterministic schema/engine contract is implemented, copy-rehearsed, independently reproduced, and installed unscheduled. No production incident packet, managed invocation, Ollama caller, or result producer is currently claimed; those remain later gates.
